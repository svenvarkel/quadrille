# Find — Specification

*2026-09-25. Status: draft for review.*

## Problem

An agent working on a 1.8-million-record CSV cannot locate anything: `--read` returns at
most 10,000 records per call, so finding the rows that mention a value means paging the
whole file through the model. Find returns the addresses of matching cells so the agent
can then `--read` or `--set` exactly those cells. It is also the prerequisite for a
useful MCP server (a later, separate piece of work).

## Scope

In scope: a `find` operation in the engine (`Sheet::find`) and a `--find` mode in the
headless CLI. Same semantics for CSV, XLSX and ODS.

Out of scope (follow-ups, not built here): TUI find dialog, regular expressions,
searching formula text, replace, MCP server, background/cancellable find jobs.

## CLI

```sh
qd FILE --find TEXT [--columns B,D] [--exact] [--ignore-case]
        [--from CELL] [--limit N] [--sheet NAME] [-d CHAR]
        [--set ... | --apply ... --dry-run] [--sort SPEC [--no-header]]
```

| Option | Meaning |
| --- | --- |
| `--find TEXT` | Cells whose value contains TEXT (case-sensitive substring). |
| `--exact` | The whole cell value must equal TEXT. `--exact --find ''` finds empty cells. |
| `--ignore-case` | Compare after Unicode lowercasing both sides (`str::to_lowercase`). This is not locale-aware matching or full Unicode case folding. |
| `--columns B,D` | Only search these columns. Comma-separated column letters, case-insensitive, no whitespace, no empty items. Duplicates are ignored. A column the file never reaches simply has no matches. Default: all. |
| `--from CELL` | Start at this cell, inclusive, in row-major order. Default `A1`. |
| `--limit N` | Stop after N matches. Default 100, minimum 1, maximum 10,000. |

`--exact`, `--ignore-case`, `--columns`, `--from` and `--limit` without `--find` are errors.
`--find` with an empty TEXT and no `--exact` is an error (it would match every cell).

Combinations:

- With `--set` / `--apply` (which still require `--dry-run`): edits are applied first,
  then find searches the edited values. Edit addresses are source coordinates, as today.
- With `--sort`: find searches the sorted view and reports **view** coordinates, like `--read`.
- With `--read`, `--output` or `--check`: error. Find is its own read-only call.

## Semantics

Search order is row-major over the current view: rows ascending (view order when
sorted), within a row columns ascending.

Searched cells in a record: every field stored in the record, plus any edited cell of
that record beyond its length (XLSX columns up to XFD that were edited). For CSV the
stored fields are the fields in the file; missing fields of ragged records are not
searched. For workbooks the stored record is the **imported rectangle** (`A1` to the
sheet's last used row/column), so blank cells inside it are searched as empty values,
while unedited virtual XLSX columns beyond it are not. `--exact --find ''` therefore
finds empty CSV fields and blank cells inside the workbook rectangle, never the
unbounded blank area.

Value searched is the value `--read` would return: edits applied; for workbook formula
cells, the cached result (empty when the file has none; possibly stale after edits to
inputs); for a new XLSX formula edit, the literal `=...` text. Formula text is not searched.

Row 1 is searched like any other record; there is no header handling.

Find does not wait for background indexing. It scans the file with its own reader and
returns as soon as `limit` matches are found. Only the scanned part of the file is
validated: invalid UTF-8 inside it is an error, invalid UTF-8 after an early exit is not
detected (the same contract as a read-only `--read`). The source stamp (and for workbooks
the original archive) is verified before and after the scan; a change is an error and no
result is emitted.

When a sort is active, find iterates the sort order (sorting already requires a full index).

## Output

```json
{
  "source": "/abs/path/file.csv",
  "find": {"text": "Tallinn", "columns": ["B"], "exact": false, "ignore_case": false,
           "from": "A1", "limit": 100},
  "coordinates": "source",
  "matches": [{"cell": "B7", "value": "Tallinn"}, {"cell": "B912", "value": "Tallinn-Nõmme"}],
  "next": "C912",
  "records_scanned": 912
}
```

- `matches`: at most `limit` entries in search order; `value` is the full cell value.
- `next`: the cell after the last match (column + 1, same row, even if that column
  does not exist), to pass as `--from` for the next page. It is non-null whenever the
  limit was hit — find does not read ahead, so the next page may be empty. `null` means
  the scan reached the end of the view. Resuming from `next` never skips or repeats a
  match, provided the view is unchanged.
- `records_scanned`: records read by this call, counting the first (possibly partially
  searched, from `--from`) and last records.
- `coordinates`: `"source"`, or `"sorted_view"` when a sort is active. Match cells are in
  these coordinates; `--set` always takes source coordinates.
- Workbooks add `sheet` and `format`. Sorted calls add the `sort` object used by `--read`.
  Calls with edits add `changes` and `dry_run` as today.

Exit status and error channel follow the existing CLI: JSON on stdout, errors on stderr,
nonzero status on failure.

## Limits

Matches are held in memory up to `limit`; values are returned in full, so output size is
bounded by `limit` times the largest matching cell. Memory otherwise does not grow with
file size. A no-match scan of the full file costs roughly one indexing pass.
